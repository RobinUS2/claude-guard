# Plan: Guard Hints for Claude — Dynamic CLAUDE.md Context

**Created:** 2026-06-07
**Status:** Planning
**Context:** Two user insights drove this plan:
1. "Can we make claude-guard expose hints to CLAUDE.md so Claude can craft commands that get auto-allowed?"
2. "Structure plans so blocking stuff is at the END of the development process"

The goal: Claude should know what the guard will and won't auto-approve, and plan accordingly.
Don't teach the guard to approve more — teach Claude to avoid friction in the first place.

---

## The Problem

Claude currently plans operations without knowing what the guard will block. It might:
- Run `git push` in the middle of a multi-step task (interrupts the flow)
- Use `export TOKEN=$(gcloud secrets ...)` when a `--token` flag form might work
- Issue `terraform apply` mid-session when it could be batched to end

The guard knows exactly what's been causing friction. Claude doesn't have access to that.

---

## Design

### `claude-guard hints` — generates a CLAUDE.md-compatible hints block

```bash
claude-guard hints [--since 7d] [--format claude-md|yaml|json]
```

**Output (default: claude-md format):**

```markdown
# Claude Guard — Auto-Approval Hints
# Generated 2026-06-07 from 7d of decision logs

## Commands That Auto-Approve (no user prompt needed)
- `git status`, `git log`, `git diff` — always instant-allow
- `git push` (non-force) — instant-allow after recent update
- `go build ./...`, `go test ./...`, `go vet ./...` — instant-allow
- `make build`, `make test`, `make lint` — instant-allow
- `find`, `grep`, `cat`, `ls` — always instant-allow

## Commands That Will Prompt the User
- `git push --force` — always requires approval (modifies remote state irreversibly)
- `terraform apply` — always requires approval (modifies cloud infrastructure)
- `export VAR=$(gcloud secrets ...)` — LLM may flag; approve once and it learns

## How to Reduce Friction: Structure Plans This Way
1. READ first: research, grep, cat, git log — all auto-approved
2. BUILD: go build, make, npm run build — auto-approved
3. TEST: go test, make test — auto-approved
4. COMMIT: git add + git commit — auto-approved
5. PUSH/DEPLOY last: git push, terraform apply — these require approval
   → Place all approval-needing steps at the END of your plan
   → Don't interrupt a build loop to push mid-task

## Pattern Guidance (from your 7d history)
- `gcloud secrets versions access` inside $() → approved 7x, first time prompts
- `make provision-diff` → usually approved, first time prompts
- Multi-line bq queries → run through BQ preflight, usually auto-approved within budget

## Session-Aware Learning
Within a session, commands approved once are auto-approved for the rest of the session.
Start with the commands most likely to prompt, approve once, then the session flows freely.
```

### How it's generated

1. Read `decisions.jsonl` for the window
2. Build allow set: tier=instant_allow or tier=session with verdict=allow
3. Build prompt set: tier=default with verdict=continue
4. Group both by canonical form
5. Generate the hints block from the known rule set + observed patterns
6. The "structure plans" section is static (derived from general knowledge of the pipeline)

### Where it goes

**Option A: Written to a static file, appended to CLAUDE.md**
```bash
claude-guard hints >> ~/.claude/CLAUDE.md
```
Robin runs this once; it's always in Claude's context.

**Option B: Written to a hints file, auto-loaded by CLAUDE.md**
```markdown
<!-- in CLAUDE.md -->
See /Users/robin/.config/claude-guard/hints.md for current guard hints.
```
`claude-guard hints --output ~/.config/claude-guard/hints.md` — regenerated daily by cron.

**Option C: Injected as a Stop hook user message**
The Stop hook already runs after every Claude turn. It could inject dynamic hints as a `userMessage`. But this is chatty — better as a background context file.

**Recommended: Option B** — static file reference in CLAUDE.md, regenerated by a daily cron job or `claude-guard review`. This way hints are always fresh without polluting CLAUDE.md itself.

## Dynamic Hints vs Static Rules

The hints file has two layers:

**Layer 1 — Static rules** (compiled from current rule set, never changes until next install):
- List of tier 2 allow rules → "these always auto-approve"
- List of tier 1 block rules → "these always block"

**Layer 2 — Dynamic patterns** (from `decisions.jsonl`, refreshed daily):
- Frequent auto-allows → "you've been doing this and it works"
- Frequent prompts → "these pattern still need approval; try X instead"
- Session-learned → "once approved, stays approved for the session"

## "Blocking at the End" Guidance

The most impactful part of the hints file is structural guidance:

```markdown
## Planning Rule: Approval-Gated Steps Go Last

The guard auto-approves all read/build/test operations.
The guard requires user approval for external state changes.

Structure every plan like this:
  ✓ Phase 1 (no prompts): read, research, build, test, lint, format
  ⚠ Phase 2 (may prompt, first time): git add, git commit  
  ⚠ Phase 3 (always prompts on new command): git push, deploy, terraform apply

Do NOT mix Phase 3 steps into Phase 1. A git push mid-build-loop kills flow.
If Phase 3 requires approval, place it as the last step of the task.
The user can then approve once and the session continues.
```

This teaches Claude to batch all external state changes to the end, reducing the number of "mid-task" interruptions.

## Open Question

Should the hints file be picked up automatically by Claude Code? Claude reads CLAUDE.md on
session start. If CLAUDE.md references the hints file path, Claude would load it. The hints
would be in Claude's context without any extra setup. This is the recommended approach —
one `echo` addition to CLAUDE.md, then hints are always current.
